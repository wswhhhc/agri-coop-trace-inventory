## 1. 引言

### 1.1 编写目的

本文档定义系统的目标、用户、功能边界、业务规则、数据要求、技术约束和验收标准，作为数据库设计、接口设计、编码、测试及毕业论文撰写的共同依据。

### 1.2 项目背景

中小型农业合作社通常采用表格或纸质记录管理农产品批次和库存，容易出现批次信息分散、库存数量不准确、临期及缺货发现不及时、产品流转过程难以查询等问题。本系统拟通过批次追溯、库存流水、规则预警和机器学习预测，形成从生产批次到消费者查询的完整业务闭环。

### 1.3 建设目标

1. 建立统一的合作社、仓库、产品、批次和质检数据管理平台。
2. 记录批次入库、出库、调拨、盘点和报损全过程。
3. 通过二维码向消费者展示可信的数据记录与流转时间线。
4. 通过规则及时发现临期、缺货、积压和质检异常。
5. 根据历史出库数据预测短期需求，为补货决策提供参考。
6. 展示 FastAPI、PostgreSQL、Redis、Celery 和机器学习的综合应用能力。

### 1.4 术语

| 术语 | 说明 |
|---|---|
| 批次 | 同一时间、产地或生产过程形成的一组农产品记录 |
| 追溯事件 | 生产、质检、入库、出库、调拨等能够说明批次流转的事件 |
| 库存流水 | 每次引起库存数量变化的不可缺失记录 |
| 规则预警 | 根据明确阈值产生的临期、缺货、积压或质检异常提醒 |
| 需求预测 | 根据历史出库数据估计未来 7 天或 30 天需求量 |
| 合成数据 | 按公开业务规则生成、且明确不是真实经营记录的实验数据 |

## 2. 系统范围与假设

### 2.1 系统边界

系统采用 Web 前后端分离模式。后台管理端服务于系统管理员、合作社管理员和仓库工作人员；公开追溯端服务于扫码消费者。

### 2.2 已采用的项目假设

1. 系统支持多个合作社，不同合作社的数据默认相互隔离。
2. 一个合作社可管理多个仓库，一个仓库可配置多名工作人员。
3. 消费者不注册账号，仅通过有效二维码查询公开追溯信息。
4. PostgreSQL 是业务数据唯一事实来源，Redis 不保存不可恢复的唯一业务数据。
5. AI 预测为辅助决策功能，不能替代管理人员的最终判断。
6. 无法取得真实商业数据时，系统使用明确标注且可复现的合成数据。
7. 本项目是教学原型，不直接用于真实食品安全认证或商业经营决策。

### 2.3 不在本期范围内

- 区块链存证。
- 物联网设备和传感器接入。
- 在线交易、订单、支付和物流配送。
- 消费者账户及会员体系。
- 短信、微信等真实消息通知。
- 农产品图像识别。
- 大语言模型聊天助手。
- 手机原生 App 和微信小程序。

## 4. 用户角色与权限

### 4.1 系统管理员

- 管理合作社、系统用户、角色和权限。
- 查看全局运行状态和操作日志。
- 不承担日常出入库工作。

### 4.2 合作社管理员

- 管理本合作社的仓库、人员、产品和预警规则。
- 查看本合作社全部批次、库存、预测、预警和报表。
- 处理预警并记录处理意见。
- 不得访问其他合作社数据。

### 4.3 仓库工作人员

- 管理被授权仓库内的批次入库、出库、调拨、盘点和报损。
- 录入批次与质检信息。
- 查看本人所属仓库的库存与预警。
- 不得修改角色、合作社或全局系统配置。

### 4.4 消费者/访客

- 无需登录。
- 通过二维码或追溯码查看允许公开的批次信息。
- 不得查看库存数量、内部备注、人员联系方式和经营报表。

### 4.5 权限矩阵

| 功能 | 系统管理员 | 合作社管理员 | 仓库工作人员 | 消费者 |
|---|---:|---:|---:|---:|
| 合作社管理 | 管理 | 查看本合作社 | 无 | 无 |
| 用户与角色 | 管理 | 管理本合作社人员 | 无 | 无 |
| 产品与批次 | 全局查看 | 管理本合作社 | 录入及查看授权范围 | 公开查看 |
| 库存业务 | 查看 | 管理本合作社 | 操作授权仓库 | 无 |
| 预警处理 | 查看 | 管理 | 查看及反馈 | 无 |
| AI预测 | 查看 | 发起及查看 | 查看授权仓库 | 无 |
| 操作日志 | 全局查看 | 查看本合作社 | 查看本人操作 | 无 |
| 扫码追溯 | 可用 | 可用 | 可用 | 可用 |

## 5. 核心业务流程

### 5.1 批次入库与追溯

1. 工作人员选择产品并创建生产批次。
2. 系统生成全局唯一的批次追溯码。
3. 工作人员录入产地、生产日期、保质期和质检信息。
4. 工作人员执行入库，系统同时更新库存和库存流水。
5. 系统生成二维码并建立对应追溯时间线。
6. 消费者扫码查看经过脱敏的批次公开信息。

### 5.2 出库与库存更新

1. 工作人员选择仓库、批次和出库数量。
2. 系统验证角色、合作社归属、仓库权限和可用库存。
3. 系统在同一数据库事务中扣减库存并新增库存流水。
4. 系统清除相关 Redis 缓存并触发预警重新计算。
5. 库存不足时拒绝操作，不允许产生负库存。

### 5.3 智能预警

1. Celery 定时任务扫描库存、保质期、质检和历史出库数据。
2. 规则引擎产生临期、缺货、积压和质检异常预警。
3. 预测模型生成未来 7 天或 30 天需求及补货参考值。
4. 合作社管理员处理预警并填写处理说明。
5. 系统保留预警状态变更和处理记录。

### 6.7 AI需求预测（P1增强功能）

本项目中的“AI”指基于历史出库数据的本地机器学习需求预测，不是调用通用对话模型或第三方 AI SDK。系统使用仓库、产品、时间、历史销量和季节性等数据训练预测模型，输出未来 7 天或 30 天的需求量和补货参考值。V1 采用 XGBoost 作为机器学习模型，移动平均作为基线模型进行效果对比。

AI 预测属于 P1 增强功能，不阻塞身份认证、权限控制、批次追溯、库存管理和规则预警等核心功能。实现时优先完成可复现的移动平均基线，再补充一种机器学习模型及异步训练流程。

| 编号 | 优先级 | 需求描述 | 验收条件 |
|---|---|---|---|
| FR-AI-001 | P1 | 生成或导入历史出库数据 | 合成数据记录生成规则、参数和随机种子 |
| FR-AI-002 | P1 | 构建时间、历史销量和季节性特征 | 训练与预测使用相同特征处理流程 |
| FR-AI-003 | P1 | 建立移动平均基线模型 | 基线结果与误差指标可复现 |
| FR-AI-004 | P1 | 训练 XGBoost 机器学习模型 | 保存模型版本，并与移动平均基线比较 |
| FR-AI-005 | P1 | 比较模型预测效果 | 展示 MAE、RMSE，并说明合成数据的局限性 |
| FR-AI-006 | P1 | 按“仓库＋产品”预测未来 7 天或 30 天需求 | 每次任务只预测一个仓库中的一个产品，并返回预测量、生成时间、模型版本和参考补货量 |
| FR-AI-007 | P1 | Celery 异步执行训练与预测 | API 快速返回任务编号，可查询任务状态和结果 |
| FR-AI-008 | P1 | 展示预测依据和风险说明 | 输出主要输入因素，不将预测包装成确定事实 |

## 7. 关键业务规则

1. 批次编号必须全局唯一，且创建后不得随意修改；用户可手动录入已有批次号，也可留空由系统自动生成。
2. 同一批次可以分布在多个仓库，库存按“仓库＋批次”统计。
3. 当前库存必须能够由全部有效库存流水计算得到。
4. 出库、报损和调拨不得导致库存小于零。
5. 库存写操作必须采用 PostgreSQL 事务；Redis 不参与最终库存判定。
6. 调拨由调出和调入两部分组成，必须全部成功或全部回滚。
7. 已完成的库存流水不直接修改；纠错通过新增调整流水实现。
8. 同一预警对象、类型和有效周期内不得产生大量重复未处理预警。
9. 公开追溯页面不得展示内部库存、成本、账号和联系方式等敏感数据。
10. AI预测结果必须标注模型版本、生成时间、数据范围和限制说明。

## 8. 数据需求

### 8.1 核心实体

- 用户、角色、权限、角色权限；每个后台用户只分配一个角色。
- 合作社、仓库、人员仓库关联。
- 产品分类、产品、生产批次、质检记录、文件及质检附件关联。
- 当前库存、库存操作、库存流水、追溯事件、幂等记录。
- 预警规则、库存预警、预警处理记录。
- 异步任务、模型版本、预测结果及每日预测明细。
- 操作日志。

### 8.2 数据完整性

- 关键业务表使用数据库主键、外键、唯一约束和非空约束。
- 数量字段不得为负，金额和数量采用适合精度的数值类型。
- 业务记录保存创建时间、更新时间和操作者。
- 多合作社表必须包含合作社标识，查询默认附加数据范围条件。
- 关键流水和审计记录原则上只追加、不物理删除。

### 8.3 合成数据规范

1. 数据生成程序、业务参数和随机种子应保留，以保证可复现。
2. 合成数据可模拟季节波动、周末效应、促销波动、临期、缺货和积压。
3. 训练集与测试集按时间顺序划分，禁止用未来数据预测过去。
4. 论文与系统页面应明确标注“合成数据，仅用于原型和算法流程验证”。
5. 不得宣称合成数据来自真实合作社，也不得据此证明真实商业效果。

## 9. 非功能需求

### 9.1 安全性

- 密码采用 Argon2 等可靠算法进行哈希，不记录明文密码。
- JWT 密钥通过环境变量提供，不提交到 Git。
- 所有输入通过 Pydantic Schema 校验。
- 数据库访问采用参数化查询或 ORM，避免拼接 SQL。
- 认证、授权和数据范围校验必须同时存在。
- 公开接口实施限流，错误响应不得暴露堆栈和数据库信息。

### 9.2 性能

以下指标以约定的本地测试环境和 50 个并发用户为基准：

- 普通分页查询接口 P95 响应时间不高于 500 ms。
- Redis 命中的公开追溯接口 P95 响应时间不高于 200 ms。
- AI任务提交接口 P95 响应时间不高于 300 ms，不等待模型执行完成。
- 所有列表接口必须分页，默认每页不超过 20 条，单页最大不超过 100 条。
- 数据大屏查询应使用缓存，缓存失效后能够正确重建。

### 9.3 可靠性与一致性

- 库存相关操作使用事务和并发控制。
- Celery 任务按至少一次投递设计，任务处理必须具备幂等性。
- 任务失败应记录原因并支持有限次数重试。
- Redis 不可用时，核心库存业务仍可运行，缓存功能允许降级。
- PostgreSQL 不可用时，禁止执行库存写操作。

### 9.4 易用性

- 后台页面保持统一导航、表格、表单和错误提示风格。
- 高风险操作要求二次确认。
- 预警必须显示类型、等级、对象、原因、时间和建议动作。
- 消费者追溯页面适配手机浏览器并避免展示内部术语。

### 9.5 可维护性

- 采用 Router、Service、Repository 分层，路由层不得直接编写复杂数据库业务。
- 公共安全、配置和基础设施代码放入明确模块，避免滥用 `utils`。
- API 输入、输出分别定义 Schema。
- 统一错误响应、日志字段和分页格式。
- 重要业务规则必须有单元测试。

## 10. 接口与技术约束

### 10.1 技术栈

| 层级 | 技术 |
|---|---|
| 后端 | Python 3.12、FastAPI、Pydantic |
| 数据访问 | SQLAlchemy、Alembic、asyncpg |
| 数据库 | PostgreSQL |
| 缓存与限流 | Redis |
| 后台任务 | Celery，Redis 作为消息代理 |
| AI与数据 | Pandas、NumPy、Scikit-learn、XGBoost、Joblib |
| 认证 | PyJWT、pwdlib/Argon2 |
| 二维码及报表 | qrcode、OpenPyXL |
| 前端 | Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios、Element Plus、ECharts |
| 前端包管理 | pnpm |
| 测试与质量 | Pytest、HTTPX、pytest-cov、Ruff、Mypy |

### 10.1.1 前端工程约定

- 前端项目目录固定为 `frontend/`，后端项目目录固定为 `backend/`，说明文档统一放在 `docs/`，三者在同一 Git 仓库中维护。
- 使用 Vite 作为构建工具，使用 Vue Router 管理页面路由，使用 Pinia 管理登录用户、权限、合作社和仓库范围等全局状态。
- 使用 Axios 封装接口请求。访问令牌只保存在前端内存中并通过 `Authorization` 请求头发送；刷新令牌由 `HttpOnly` Cookie 保存，并统一处理令牌刷新请求。
- 开发环境前端端口固定为 `5173`，后端 CORS 按该地址进行明确配置。
- 选择上述方案的原因是：Vue 3 与现有需求匹配，Vite 配置简单且启动快速，Pinia 适合权限等共享状态，Axios 便于统一处理认证和错误，单仓库便于毕业设计项目的开发、联调和复现。

### 10.2 API约定

- API 统一使用 `/api/v1` 前缀。
- 使用 JSON 作为主要请求和响应格式。
- 资源命名采用复数名词，列表接口提供分页和筛选。
- 新增返回 201，异步任务返回 202，无内容删除返回 204。
- 400 表示请求语义错误，401 表示未登录，403 表示无权限，404 表示资源不存在，409 表示业务冲突，422 表示参数校验失败，429 表示访问过频。
- 错误响应统一包含机器可读错误码、提示信息和可选详情。
- OpenAPI/Swagger 作为接口文档和调试入口。

### 10.3 项目结构

| 目录 | 职责 |
|---|---|
| `backend/app/routers` | API路由与请求边界 |

| `backend/app/services` | 业务用例与事务协调 |
| `backend/app/repositories` | 数据访问封装 |

| `backend/app/tasks` | Celery后台和定时任务 |
| `backend/app/ml` | 数据处理、训练、预测和模型管理 |
| `backend/app/core` | 配置、安全、权限和异常处理 |
| `backend/tests/unit` | 单元测试 |
| `backend/tests/integration` | 数据库、缓存及API集成测试 |

### 10.4 常用命令

以下命令在 `backend/` 目录中执行：

- 同步依赖：`uv sync`
- 启动后端：`uv run uvicorn app.main:app --reload`
- Windows开发环境启动Celery：`uv run celery -A app.infrastructure.celery worker --pool=solo --loglevel=info`
- 运行测试：`uv run pytest`
- 测试覆盖率：`uv run pytest --cov=app --cov-report=term-missing`
- 代码检查：`uv run ruff check .`
- 类型检查：`uv run mypy app`
- 合并前门禁（项目根目录）：`uv run python backend/scripts/test_gate.py`；该命令要求 PostgreSQL、Redis 可用，并校验全项目覆盖率不低于 70%、公共关键模块不低于 80%。

## 12. 总体验收标准

满足以下条件时，系统可认为达到毕业设计原型的核心要求：

1. 三类后台用户可以通过统一入口登录，权限和数据范围隔离有效。
2. 可以完成合作社、仓库、产品、批次和质检信息管理。
3. 可以完成入库、出库、盘点和报损，且库存与流水始终一致。
4. 并发及重复请求不会产生负库存或重复库存变更。
5. 消费者可以扫码查看脱敏后的完整批次追溯时间线。
6. Redis缓存可以命中、过期并在数据修改后正确失效。
7. 系统能够产生并处理临期、缺货、积压和质检异常预警。
8. Celery能够异步执行预警扫描和AI预测任务，并记录状态。
9. 至少一种机器学习模型完成训练、预测和指标评估，并与基线方法比较。
10. AI实验明确披露合成数据来源和结论限制。
11. 系统提供库存、预警和预测可视化，以及操作审计记录。
12. 核心测试、代码检查和接口文档能够正常运行。

## 13. 开发边界

### 13.1 始终执行

- 修改功能前先更新需求或设计说明。
- 所有外部输入在接口边界进行校验。
- 库存变更必须经过Service层和数据库事务。
- 提交前运行与变更相关的测试和代码检查。
- 使用中文、单一职责的Git提交说明。

### 13.2 需要先确认

- 增加新的用户角色或核心业务模块。
- 修改数据库核心实体或批次编号规则。
- 增加第三方服务、付费API或新的运行依赖。
- 改变AI预测目标、数据来源或评估方法。

### 13.3 禁止事项

- 提交 `.env`、密码、密钥和真实个人信息。
- 将Redis作为库存数量的唯一事实来源。
- 绕过权限与合作社数据范围校验直接访问数据。
- 修改或删除库存流水以掩盖历史操作。
- 将合成数据描述为真实经营数据。
- 删除失败测试以获得表面通过结果。

## 14. 已确认与待确认事项

### 14.1 已确认

1. 访问令牌放在响应体并由前端内存保存，刷新令牌通过 HttpOnly Cookie 传递，会话状态保存在 Redis。
2. AI 模型和预测粒度为“仓库＋产品”，每次任务只处理一个产品，预测周期支持 7 天和 30 天。
3. 质检文字结果为 P0，质检附件为 P1；初始数据库预留文件及附件关联结构。
4. 仓库调拨为 P1；初始数据库通过库存操作记录关联同一调拨的调出、调入流水。
5. 演示数据全部为可复现的合成数据，固定随机种子为 `20260904`。
6. 前端采用 Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios、Element Plus 和 ECharts，使用 pnpm 管理前端依赖。
7. 前后端采用同一 Git 仓库管理，前端目录为 `frontend/`，后端目录为 `backend/`，文档目录为 `docs/`；前端开发端口固定为 `5173`。
8. 系统管理员仅负责平台、合作社、用户、角色和权限等管理，不执行日常库存写操作；入库、出库、调拨、盘点和报损由具备相应权限的业务人员执行。

### 14.2 可选需求验证活动

1. 可与农业专业教师进行需求访谈，用于验证库存管理、批次追溯和预警流程是否符合业务理解；访谈属于需求验证活动，不阻塞当前软件开发。

### 14.3 AI实现方案（已确认）

1. V1 采用 XGBoost，移动平均基线模型保持不变。
2. 统一训练、预测、误差计算和模型版本保存流程；数据库保留随机森林枚举值以支持后续扩展，但不作为 V1 演示模型。
