# ADR-001：使用范围隔离的 Redis 查询缓存

## 状态

已接受

## 日期

2026-09-07

## 背景

产品、仓库、批次、模型等查询存在重复读取和聚合开销，但库存最终数量、流水、审计和预警状态对时效性要求较高。认证权限也不能依赖可变缓存作为唯一安全依据。

## 决策

采用 PostgreSQL 主数据 + Redis Cache-Aside。Redis 只保存可重建的 API Schema 响应，缓存键摘要包含合作社、角色、可见仓库集合、资源 ID 和完整查询参数。所有读接口先完成权限与范围校验，再读取缓存；写事务提交成功后按合作社或全局范围失效相关 key。TTL 使用随机抖动，热点重建使用短时互斥锁。

首批缓存产品分类、产品、仓库、角色/权限字典；随后缓存模型版本、已生成预测结果、批次详情和常用质检列表。库存、流水、审计、任务状态和预警查询保持 PostgreSQL 实时读取。

## 未采用的方案

- 不把 Redis 作为业务数据主库，避免缓存丢失导致库存或历史记录不可恢复。
- 不把所有分页和关键词组合都缓存，避免用户输入造成 key 数量和内存无限增长。
- 不缓存用户实时权限上下文，避免角色或仓库授权变更后出现越权窗口。
- 不缓存预警列表，除非后续指标证明收益足够覆盖状态陈旧风险。

## 后果

- 命中缓存的读请求可以减少 PostgreSQL 重复查询；Redis 故障时普通查询自动回源。
- 主数据和模型写入需要维护对应资源的失效范围；新增资源时必须补充失效测试。
- TTL 抖动和单键互斥降低集中失效与缓存击穿风险，但不能替代性能压测和 Redis 内存监控。
