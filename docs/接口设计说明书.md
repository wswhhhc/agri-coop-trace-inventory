## 1. 文档目的

本文档是前端、后端和测试之间的接口契约。接口实现、前端类型和自动化测试必须与本文档保持一致。任何字段删除、字段类型修改、状态枚举修改或响应结构变化，都应先更新并评审本文档。

接口设计目标：

1. 相同类型的接口保持一致的命名、分页、响应和错误格式。
2. 身份认证、角色权限和合作社数据范围边界明确。
3. 库存写操作具备事务一致性和请求幂等能力。
4. Celery耗时任务采用统一异步任务协议。
5. 前端能够仅根据本文档完成页面、类型和请求层开发。

## 2. 全局约定

### 2.1 基础地址

| 环境 | 地址示例 |
|---|---|
| 本地开发 | `http://localhost:8000/api/v1` |
| API文档 | `http://localhost:8000/docs` |
| OpenAPI JSON | `http://localhost:8000/openapi.json` |

本文档中的路径均省略 `/api/v1` 前缀。例如 `GET /products` 的完整路径为 `GET /api/v1/products`。

### 2.2 传输格式

- 默认请求类型：`Content-Type: application/json`。
- 默认响应类型：`application/json; charset=utf-8`。
- 文件上传：`multipart/form-data`。
- 二维码图片：`image/png`。
- 所有请求和响应采用 UTF-8。

### 2.3 字段命名

- 对外JSON字段和查询参数统一使用 `camelCase`，例如 `createdAt`、`pageSize`。
- Python内部变量和数据库字段可以使用 `snake_case`，由Pydantic别名完成转换。
- 布尔字段使用 `is`、`has`、`can` 前缀。
- 枚举值统一使用 `UPPER_SNAKE_CASE`。
- 资源ID统一使用UUID字符串。

### 2.4 日期、时间与数量

| 类型 | 格式 | 示例 |
|---|---|---|
| 日期 | ISO 8601日期 | `2026-09-04` |
| 时间 | ISO 8601并包含时区 | `2026-09-04T08:30:00+08:00` |
| UUID | 标准UUID字符串 | `1b2d26c5-6e44-46de-a9d8-801f9ff19f40` |
| 数量 | JSON number，最多3位小数 | `125.500` |

服务端保存UTC时间，响应可统一输出带时区的ISO 8601时间。前端负责按用户时区显示。

### 2.5 空值与字段缺省

- 响应中可为空的字段使用 `null`。
- `PATCH` 请求中未提供字段表示“不修改”。
- `PATCH` 请求中显式提供 `null` 表示“清空字段”，仅对允许清空的字段有效。
- 前端不得用空字符串代替 `null`。

### 2.6 删除与停用策略

- 合作社、用户、仓库、产品和批次不提供物理删除接口，通过 `PATCH` 修改状态。
- 库存流水、追溯事件、预警处理记录和审计日志只追加，不提供修改历史或删除接口。
- 只有尚未被任何业务记录引用的辅助配置，后续才允许考虑物理删除。

### 2.7 通用请求头

| 请求头 | 是否必需 | 用途 |
|---|---:|---|
| `Authorization: Bearer <token>` | 后台接口必需 | JWT访问令牌 |
| `Idempotency-Key` | 库存写接口必需 | 防止重复入库、出库、调拨、盘点或报损 |
| `X-Request-ID` | 可选 | 前端生成的请求追踪ID；缺省时由后端生成 |
| `Accept-Language` | 可选 | 默认 `zh-CN` |

所有响应返回 `X-Request-ID`，便于前后端通过日志定位同一次请求。

## 3. 认证与数据权限

### 3.1 角色枚举

| 枚举值 | 中文名称 | 说明 |
|---|---|---|
| `SYSTEM_ADMIN` | 系统管理员 | 管理全局合作社、角色和系统日志 |
| `COOPERATIVE_ADMIN` | 合作社管理员 | 管理本合作社业务和人员 |
| `WAREHOUSE_STAFF` | 仓库工作人员 | 操作被授权仓库的批次和库存 |
| `PUBLIC` | 消费者/访客 | 仅访问公开追溯接口，不签发登录令牌 |

### 3.2 JWT约定

访问令牌采用Bearer Token。JWT仅保存必要身份信息，不在令牌中保存完整权限列表或全部仓库ID，避免权限变更后旧令牌长期失效不及时。

JWT Claims 正式约定如下：

```json
{
  "sub": "8c31807d-878f-4a23-a75e-7d5e6195e4f0",
  "sid": "8457eaed-1d2c-43ae-89c5-57eb458e39c6",
  "jti": "1e2f3a4b-5c6d-47e8-9f01-23456789abcd",
  "role": "COOPERATIVE_ADMIN",
  "cooperativeId": "3bc95478-d8f0-4e47-b5c4-b4473be52b17",
  "iat": 1788480000,
  "exp": 1788481800
}
```

- `sub`：用户ID。
- `sid`：登录会话ID。同一次登录会话及其刷新得到的访问令牌保持不变，用于Redis会话控制和退出失效；Redis会话键使用 `auth:session:{sid}`。
- `jti`：当前JWT的唯一标识。每次签发访问令牌时重新生成，用于单令牌追踪、审计以及必要时的单令牌撤销。
- `cooperativeId`：系统管理员可为 `null`。
- 仓库权限每次从缓存或数据库读取，不完全信任令牌中的可变权限。

### 3.3 令牌保存方式

- 访问令牌由前端保存在内存中，通过Authorization请求头发送。
- 刷新令牌通过 `HttpOnly` Cookie保存，前端JavaScript不能直接读取。
- 刷新访问令牌时保留原 `sid`，并为新访问令牌生成新的 `jti`；刷新令牌轮换后旧令牌立即失效。
- 生产环境Cookie启用 `Secure`，并设置合适的 `SameSite` 与CORS策略。
- 退出时服务端撤销会话并清除刷新Cookie。

### 3.4 数据范围规则

1. 系统管理员可跨合作社查询管理数据，但默认不执行库存业务。
2. 合作社管理员只能操作Token所属合作社的数据。
3. 仓库工作人员只能操作被授权仓库的数据。
4. 服务端根据当前用户推导合作社范围，不能只相信请求体中的 `cooperativeId`。
5. 无权限访问他人资源统一返回404，减少资源ID枚举风险；功能级权限不足返回403。

### 4.1 单个资源成功响应

```json
{
  "data": {
    "id": "1b2d26c5-6e44-46de-a9d8-801f9ff19f40",
    "name": "示例资源"
  }
}
```

### 4.2 列表成功响应

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

### 4.3 分页参数

| 参数 | 类型 | 默认值 | 限制 | 说明 |
|---|---|---:|---|---|
| `page` | integer | 1 | ≥1 | 页码 |
| `pageSize` | integer | 20 | 1—100 | 每页数量 |
| `sortBy` | string | `createdAt` | 端点白名单 | 排序字段 |
| `sortOrder` | enum | `DESC` | `ASC`/`DESC` | 排序方向 |

耗时任务统一返回202：

```json

  }
}
```

### 4.5 错误响应

所有错误使用同一结构：

```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",

  }
}
```

错误消息用于展示，前端业务分支必须依据稳定的 `error.code`，不得匹配中文提示文本。

## 6. 身份认证接口

### 6.1 接口清单

| 方法 | 路径 | 权限 | 成功状态 | 对应需求 |
|---|---|---|---:|---|
| POST | `/auth/login` | 公开 | 200 | FR-AUTH-001 |
| POST | `/auth/refresh` | 刷新Cookie | 200 | FR-AUTH-002 |
| POST | `/auth/logout` | 已登录 | 204 | FR-AUTH-002 |
| GET | `/auth/me` | 已登录 | 200 | FR-AUTH-004、005 |

### 6.2 登录

`POST /auth/login`

请求：

```json
{
  "username": "coop_admin",
  "password": "用户输入的密码"
}
```

响应：

```json
{
  "data": {
    "accessToken": "eyJhbGciOi...",
    "tokenType": "Bearer",
    "expiresIn": 1800,
    "user": {
      "id": "8c31807d-878f-4a23-a75e-7d5e6195e4f0",
      "username": "coop_admin",
      "displayName": "合作社管理员",
      "role": "COOPERATIVE_ADMIN",
      "cooperativeId": "3bc95478-d8f0-4e47-b5c4-b4473be52b17",
      "status": "ACTIVE"
    },
    "permissions": [
      "user:manage", "warehouse:manage", "product:manage", "batch:manage",
      "inventory:read", "trace:read", "alert:read",
      "alert:handle", "model:read", "model:manage", "audit:read"
    ]
  }
}
```

规则：

- 登录失败统一返回 `INVALID_CREDENTIALS`，不区分用户名不存在或密码错误。
- 登录成功通过 `Set-Cookie` 写入刷新令牌。
- 连续失败达到阈值后返回429和 `RATE_LIMIT_EXCEEDED`。

### 6.3 刷新访问令牌

`POST /auth/refresh`

- 请求体为空，浏览器自动携带刷新Cookie。
- 服务端轮换刷新令牌，旧令牌立即失效。
- 响应结构与登录接口中的令牌部分一致。

### 6.4 当前用户

`GET /auth/me`

响应除用户信息外，应包含当前权限和被授权仓库：

```json
{
  "data": {
    "id": "8c31807d-878f-4a23-a75e-7d5e6195e4f0",
    "username": "warehouse_01",
    "displayName": "一号仓库员",
    "role": "WAREHOUSE_STAFF",
    "cooperativeId": "3bc95478-d8f0-4e47-b5c4-b4473be52b17",
    "warehouseIds": ["ff9d2ff9-ac17-4ad8-8719-f680ec36967d"],
    "permissions": ["batch:manage", "inventory:read", "inventory:write", "trace:read", "alert:read", "alert:handle", "model:read"],
    "status": "ACTIVE"
  }
}
```

## 7. 合作社、用户与权限接口

### 7.1 合作社

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/cooperatives` | 系统管理员 | 分页查询合作社 |
| POST | `/cooperatives` | 系统管理员 | 创建合作社 |
| GET | `/cooperatives/{cooperativeId}` | 系统管理员、本合作社管理员 | 查询详情 |
| PATCH | `/cooperatives/{cooperativeId}` | 系统管理员 | 修改资料或状态 |

创建请求 `CooperativeCreate`：

| 字段 | 类型 | 必需 | 规则 |
|---|---|---:|---|
| `code` | string | 是 | 2—32字符，全局唯一，创建后不可修改 |
| `name` | string | 是 | 2—100字符 |
| `address` | string | 否 | 最多255字符 |
| `contactName` | string | 否 | 最多50字符，仅内部使用 |
| `contactPhone` | string | 否 | 合法手机号格式，仅内部使用 |

修改请求只允许提供 `name`、`address`、`contactName`、`contactPhone`、`status`。

### 7.2 用户

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/users` | 系统管理员、合作社管理员 | 按数据范围分页查询用户 |
| POST | `/users` | 系统管理员、合作社管理员 | 创建用户 |
| GET | `/users/{userId}` | 系统管理员、合作社管理员、本人 | 查询用户 |
| PATCH | `/users/{userId}` | 系统管理员、合作社管理员 | 修改姓名、角色或状态 |
| PUT | `/users/{userId}/warehouses` | 合作社管理员 | 完整替换仓库授权 |
| POST | `/users/{userId}/password-resets` | 系统管理员、合作社管理员 | 生成一次性重置凭据 |

创建用户请求：

```json
{
  "username": "warehouse_01",
  "displayName": "一号仓库员",
  "role": "WAREHOUSE_STAFF",
  "cooperativeId": "3bc95478-d8f0-4e47-b5c4-b4473be52b17",
  "warehouseIds": ["ff9d2ff9-ac17-4ad8-8719-f680ec36967d"]
}
```

响应包含一次性初始密码，仅在创建成功时返回一次；日志不得记录该密码。

权限规则：

- 系统管理员可以创建系统管理员、合作社管理员和仓库工作人员。
- 合作社管理员只能在本合作社创建仓库工作人员，不能创建系统管理员或其他合作社管理员。
- 合作社管理员不能将本人或他人提权为系统管理员。
- 请求中的 `cooperativeId` 必须与当前管理范围匹配，否则返回404。

### 7.3 角色与权限

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/roles` | 系统管理员 | 查询角色 |
| GET | `/permissions` | 系统管理员 | 查询权限点 |
| PUT | `/roles/{roleId}/permissions` | 系统管理员 | 完整替换角色权限集合 |

权限替换请求：

```json
{
  "permissionIds": [
    "ea9c607d-a83d-47eb-9354-8cbc0de9e3a9",
    "25f35742-6174-4854-bcab-b5523ccfc64f"
  ]
}
```

系统内置角色编码不得修改或删除，只允许调整可配置权限集合。

## 8. 仓库接口

| 方法 | 路径 | 权限 | 成功状态 | 说明 |
|---|---|---|---:|---|
| GET | `/warehouses` | 已登录 | 200 | 按权限查询仓库 |
| POST | `/warehouses` | 合作社管理员 | 201 | 创建仓库 |
| GET | `/warehouses/{warehouseId}` | 有仓库权限 | 200 | 查询仓库详情 |
| PATCH | `/warehouses/{warehouseId}` | 合作社管理员 | 200 | 修改资料或状态 |

查询参数：`keyword`、`status`、`page`、`pageSize`、`sortBy`、`sortOrder`。

创建请求：

```json
{
  "code": "WH-JL-001",
  "name": "吉林一号仓库",
  "address": "吉林省吉林市",
  "managerName": "张某",
  "remark": null
}
```

### 12.8 幂等处理协议

1. 前端为一次业务意图生成UUID作为 `Idempotency-Key`，网络重试必须复用同一个键。
2. 服务端在PostgreSQL中通过唯一约束原子占用该键，不能使用“先查询、再插入”。
3. 相同键和相同请求体重复到达时，返回第一次成功响应，不重复改变库存。
4. 相同键对应不同请求体时返回422和 `IDEMPOTENCY_PAYLOAD_MISMATCH`。
5. 首次请求仍在处理中时返回409和 `IDEMPOTENCY_IN_PROGRESS`。
6. 库存接口幂等记录至少保留7天。

当前库存业务切片已实现上述查询、入库、出库、调拨、盘点和报损接口。库存写操作使用 PostgreSQL 事务和行锁，当前库存、操作头与不可变流水同步写入；集成测试需要 PostgreSQL/Redis 测试基础设施后执行。

## 18. 关键联调时序

### 18.1 登录与页面初始化

```text
前端 → POST /auth/login → 后端验证账号及合作社状态
前端 ← accessToken + refreshCookie + user
前端 → GET /auth/me → 后端返回最新权限和仓库范围
前端 ← 根据permissions生成菜单和按钮
```

前端隐藏按钮仅改善体验，不能替代后端权限校验。

### 18.2 出库时序

```text
前端生成 Idempotency-Key
前端 → POST /inventory-issues
后端 → 验证身份、角色、合作社和仓库权限
后端 → 原子占用幂等键
后端 → PostgreSQL事务锁定库存、校验数量、扣减库存、写入流水
后端 → 提交事务
后端 → 删除Redis相关缓存并提交预警重算任务
前端 ← 201 + 库存流水结果
```

### 18.3 AI异步任务时序

```text
前端 → POST /forecast-tasks
后端 → 创建任务记录并投递Celery
前端 ← 202 + taskId + statusUrl
前端 → 首次等待2秒后 GET /tasks/{taskId}
前端 ← PENDING/RUNNING/SUCCESS/FAILURE/RETRY
前端 → 成功后 GET /forecast-results/{resultId}
```

前端轮询采用2秒、3秒、5秒的渐进间隔，页面关闭时停止轮询。

### 18.4 访问令牌刷新

1. 普通接口返回401和 `TOKEN_EXPIRED`。
2. 前端只允许一个刷新请求执行，其他失败请求等待该结果。
3. 刷新成功后，以新访问令牌重试原请求一次。
4. 刷新失败时清理本地状态并跳转登录页。
5. 禁止无限刷新或无限重试。

## 19. CORS、缓存与限流

### 19.1 CORS

- 开发环境前端地址固定为 `http://localhost:5173`，仅允许明确配置该地址。
- 使用刷新Cookie时必须配置 `allowCredentials=true`，不能同时使用通配来源 `*`。
- 生产环境只允许正式前端域名。

### 19.2 Redis缓存

| 数据 | V1默认TTL | 失效条件 |
|---|---:|---|
| 公开批次追溯 | 10分钟 | 批次、质检或追溯事件变化 |
| 数据大屏汇总 | 5分钟 | 相关库存或预警变化 |
| 用户权限 | 5分钟 | 用户角色、状态或仓库授权变化 |

权限缓存不可用时允许回源PostgreSQL，公开追溯和数据大屏等非认证缓存可降级；登录会话校验、刷新令牌轮换、退出撤销和登录失败限流属于认证闭环，Redis不可用时相关认证请求失败关闭。无法确认身份时返回503和 `DEPENDENCY_UNAVAILABLE`，不将基础设施故障误判为401；库存写入和最终库存判断始终依赖PostgreSQL。

### 19.3 限流

| 接口 | V1默认限制 |
|---|---|
| 登录 | 同一账号或IP每分钟10次 |
| 公开追溯 | 同一IP每分钟60次 |
| 二维码图片 | 同一IP每分钟120次 |
| 手动AI任务 | 同一用户每分钟5次 |

超过限制返回429，并可通过 `Retry-After` 告知建议等待秒数。

## 20. 契约测试与验收

### 20.1 后端必须验证

- OpenAPI中的路径、方法、字段名、类型和状态码与本文档一致。
- 所有列表接口均支持统一分页并在空结果时返回空数组。
- 所有错误均符合统一错误结构。
- 401、403、404的数据权限语义一致。
- 跨合作社和跨仓库访问被阻止。
- 库存写接口缺少幂等键时返回422。
- 相同幂等键重试不重复改变库存。
- 并发出库不会产生负库存。
- Redis缓存修改后正确失效。
- Celery任务可查询成功和失败状态。

### 20.2 前端必须验证

- 请求层统一附加访问令牌和请求追踪ID。
- 库存写操作一次业务意图复用同一幂等键。
- 401触发单次刷新，刷新失败后退出登录。
- 403、404、409、422和429具有明确用户提示。
- 分页、筛选和排序参数与接口约定一致。
- 异步任务能够轮询、停止并展示失败原因。
- 前端类型定义与OpenAPI生成类型不存在冲突。

### 20.3 联调完成标准

1. 每个页面都能映射到本文档中的确定接口。
2. 每个接口都具有明确角色、数据范围、请求、响应和错误语义。
3. Swagger可以按角色完成主要业务流程演示。
4. 前后端不通过猜测字段名、解析中文错误文本或依赖未记录行为完成联调。
5. 接口变更先修改文档及OpenAPI，再修改调用方。

## 21. 版本与变更规则

- V1阶段只维护 `/api/v1`，不并行维护多个实验版本。
- 新增可选字段通常视为兼容变更。
- 删除字段、重命名字段、修改字段类型或枚举语义属于破坏性变更。
- 破坏性变更必须评审，并同步修改本文档、Pydantic Schema、OpenAPI、前端类型和契约测试。
- 已发布接口不得静默改变错误码或排序行为。

## 22. 已确认与待确认事项

### 22.1 已确认

1. 访问令牌由响应体返回并保存在前端内存，刷新令牌使用 HttpOnly Cookie，服务端会话保存在 Redis。
2. AI 模型和预测粒度固定为“仓库＋产品”，每个训练或预测任务只处理一个产品，周期支持 7 天和 30 天。
3. 质检附件为 P1，但 V1 数据库预留文件和质检附件关联表。
4. 调拨为 P1，第一版优先完成入库、出库、盘点和报损；V1 数据库仍支持一项调拨操作关联两条库存流水。
5. 前端采用 Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios、Element Plus 和 ECharts，使用 pnpm 管理前端依赖。
6. 前后端采用同一 Git 仓库管理，前端目录为 `frontend/`，后端目录为 `backend/`，文档目录为 `docs/`；前端开发端口固定为 `5173`。
7. 系统管理员仅负责平台、合作社、用户、角色和权限等管理，不执行日常库存写操作；库存写操作由具备相应权限的业务人员执行。
8. V1 机器学习模型采用 XGBoost，移动平均作为基线模型；`model:read` 用于查看模型和预测结果，`model:manage` 用于训练和激活模型。

### 22.2 待确认

当前无影响接口实现的技术待确认项。
