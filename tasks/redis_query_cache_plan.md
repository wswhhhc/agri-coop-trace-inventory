# Redis 查询加速专项计划书

## 1. 目标

在 PostgreSQL 仍作为唯一事实来源的前提下，为项目中高频、读多写少且允许短暂陈旧的数据查询增加 Redis Cache-Aside 缓存，降低重复 SQL 查询和聚合查询耗时，并保证权限隔离、缓存失效和 Redis 故障回源行为可验证。

本计划只规划后端查询加速，不把 Redis 作为库存、流水、审计等不可替代业务数据的唯一存储。

## 2. 当前基线

- 已接入公开追溯缓存：`/public/traces/{traceCode}` 及二维码接口复用该查询缓存。
- 已接入大屏五个统计接口：汇总、库存趋势、预警分布、产品排行、预测对比。
- Redis 已用于认证会话、登录失败计数和公开接口 IP 限流，这些不是业务查询结果缓存。
- `permission_cache_ttl_seconds` 已有配置，但当前权限和仓库范围仍由 PostgreSQL 实时解析，尚未实现权限缓存。
- 现有缓存已具备 Redis 异常回源、JSON 解析失败删除和 Schema 校验失败回源能力，新增模块应复用并统一。

## 3. 设计原则

1. PostgreSQL 是唯一事实来源，Redis 只保存可重建的查询结果。
2. 使用 Cache-Aside：先查缓存，未命中查 PostgreSQL，成功后写入 Redis。
3. 所有写事务提交成功后再删除相关缓存，禁止在事务提交前失效。
4. 缓存键必须包含合作社、可见仓库范围、资源 ID、筛选条件、排序和分页参数。
5. Redis 不可用、缓存损坏或 Schema 不兼容时，自动回源 PostgreSQL，不影响业务读取。
6. 默认不缓存包含用户个人信息、实时库存判断或强一致状态的数据。
7. 对分页列表设置页码、页大小、缓存容量和 TTL 上限，避免缓存组合无限增长。
8. TTL 使用随机抖动，避免同一批缓存同时过期造成缓存雪崩；热点缓存允许在临近过期时异步刷新。
9. 缓存重建使用短时互斥锁或单飞机制，同一缓存键同时只允许一个请求负责重建。

## 4. 缓存范围和优先级

### P0：优先接入

| 数据查询 | 建议缓存内容 | 建议 TTL | 失效触发 |
|---|---|---:|---|
| 产品分类详情及常用列表 | 合作社范围内分类数据 | 30～60 分钟 | 分类新增、修改 |
| 产品详情及下拉/常用列表 | 产品基本信息，不缓存任意组合分页 | 10～30 分钟 | 产品新增、修改、分类变化 |
| 仓库详情及常用列表 | 合作社/授权仓库范围内仓库数据 | 10～30 分钟 | 仓库新增、修改、状态变化 |
| 权限字典 | 全局权限编码和名称 | 30～60 分钟 | 权限定义变更或部署 |
| 角色及角色权限 | 系统管理员可见的角色权限关系 | 10～30 分钟 | 角色权限绑定修改 |
| 当前启用模型版本 | 合作社、仓库、产品粒度的模型版本 | 5～15 分钟 | 模型激活、模型版本变更 |

产品、分类和仓库的任意搜索条件不建议全部缓存，优先为前端下拉、首页常用筛选和详情查询提供缓存。
实际 TTL 使用基准值加随机抖动，例如基准 TTL 的 `±10%`；具体范围由 R0 压测和 Redis 内存情况确定。

### P1：验证后接入

| 数据查询 | 建议缓存内容 | 建议 TTL | 注意事项 |
|---|---|---:|---|
| 批次详情 | 单个批次及其稳定关联数据 | 1～5 分钟 | 批次、质检、库存或追溯事件变化后失效 |
| 质检列表/详情 | 最近查询或单批次质检数据 | 1～5 分钟 | 新增和更正质检后失效 |
| 预测结果详情 | 已完成且不可变的预测结果 | 5～15 分钟 | 新结果生成或结果修正后失效 |
| 预警详情 | 单条预警详情 | 5～30 秒 | 扫描、处理、状态变化后失效 |

预警列表只在访问量和 PostgreSQL 压力证明有收益后再缓存；其状态变化较频繁，默认优先保留实时查询。

### 保持 PostgreSQL 实时查询

- 当前库存数量及库存风险判断。
- 入库、出库、调拨、盘点、报损流水及详情。
- 审计日志。
- Celery 任务状态。
- 文件下载内容。
- 用户禁用状态、认证上下文和可变仓库权限。

认证会话仍使用 Redis，但不能把缓存的用户权限当作安全判断的唯一依据。若以后缓存认证上下文，必须使用短 TTL、权限版本号和用户/角色/仓库变更失效机制。

## 5. 实施阶段

### R0：基线和指标

- 统计候选接口调用量、P95/P99 延迟、数据库查询次数和慢查询。
- 明确前端实际高频请求，避免缓存低频接口。
- 记录当前 Redis 连接、超时、内存和 key 数量基线。
- 冻结每类数据的允许陈旧时间和权限范围语义。

验收：形成接口基线表，明确每个候选接口是否值得缓存。

### R1：统一缓存基础设施

- 抽取通用 Cache-Aside 封装，统一 JSON 序列化、TTL、异常降级和删除行为。
- 统一计算带随机抖动的有效 TTL，禁止同一批次写入的缓存使用完全相同的过期时间。
- 统一缓存键构造器，支持资源名、合作社、仓库范围、筛选条件和版本字段。
- 增加 Schema 反序列化校验，校验失败删除缓存并回源。
- 为高并发缓存增加短时互斥/单飞机制，先应用于昂贵聚合查询和热点详情。
- 为热点 key 增加“提前刷新”策略：剩余 TTL 低于阈值时由后台任务异步重建，刷新失败不阻塞正常回源。
- 对批量刷新设置并发上限和随机延迟，禁止部署或定时任务一次性刷新全量 key。
- 为缓存命中、未命中、回源、写入失败和删除失败增加结构化日志或指标，不记录业务敏感数据。

验收：现有追溯和 dashboard 缓存迁移后行为不变，Redis 故障仍能回源。

### R2：接入基础字典和常用资源

- 接入产品分类、产品详情/常用列表、仓库详情/常用列表。
- 接入权限字典和角色权限查询。
- 在产品、分类、仓库和角色权限写操作提交后执行精确或版本化失效。
- 对列表缓存限制只缓存白名单筛选组合，避免任意关键词产生大量 key。

验收：覆盖命中、未命中、更新后失效、合作社隔离、仓库权限隔离和 Redis 故障回源。

### R3：接入模型和预测结果查询

- 缓存当前启用模型版本和常用模型版本详情。
- 对已完成预测结果详情进行短时缓存。
- 模型激活、新预测结果落库或结果修正后失效相关 key。
- 不缓存训练中的任务状态作为最终状态依据。

验收：模型激活后不会继续返回旧模型；不同合作社、仓库和产品的数据不串用。

### R4：接入批次和质检读查询

- 先接入批次详情，再评估批次列表和质检列表。
- 统一处理批次、质检、库存和追溯事件之间的交叉失效。
- 对详情缓存设置较短 TTL，并限制缓存响应字段，不缓存不必要的敏感字段。

验收：批次修改、质检新增/更正、库存变更后，相关查询不会长期返回旧数据。

### R5：按指标决定是否接入预警列表

- 观察预警列表的访问量、状态变更频率和查询耗时。
- 只有在收益明确时缓存最近页或详情，TTL 默认不超过 30 秒。
- 扫描任务创建预警、人工处理预警后执行失效。

验收：缓存不会妨碍预警处理闭环，也不会让用户长时间看不到状态变化。

### R6：性能验证和上线复查

- 对缓存命中、未命中和 Redis 故障三种场景进行接口压测。
- 验证带 TTL 随机抖动时的过期分布，模拟批量缓存同时失效和热点缓存提前刷新。
- 验证互斥重建在并发请求下不会重复击穿 PostgreSQL；验证刷新失败可以回源。
- 对比 PostgreSQL 查询次数、P95/P99 延迟、Redis 命中率和内存增长。
- 执行全量单元测试、PostgreSQL/Redis 集成测试、Ruff、mypy 和严格门禁。
- 检查缓存键是否包含完整权限范围，检查日志是否泄露 Token、密码或敏感业务数据。
- 编写回滚方案：通过配置关闭新增缓存，业务自动回源 PostgreSQL。

## 6. 推荐缓存键规范

统一使用现有 `redis_key_prefix`，建议按以下形式组织：

```text
{prefix}query:{resource}:{scope_hash}:{filter_hash}
```

其中：

- `resource`：固定资源名，例如 `product-detail`、`warehouse-list`。
- `scope_hash`：合作社 ID、角色可见仓库集合、必要时的权限版本。
- `filter_hash`：资源 ID、筛选、排序、分页等规范化参数。
- 不直接把用户输入原文拼入 key，避免 key 过长并统一编码。

## 7. 测试要求

- 单元测试：命中、未命中、TTL、JSON 损坏、Schema 不匹配、Redis 异常。
- 权限测试：合作社隔离、仓库集合隔离、系统管理员全局范围。
- 失效测试：新增、修改、状态变化、模型激活、预警处理后缓存删除。
- 集成测试：真实 Redis 与 PostgreSQL 联合验证回源和事务提交顺序。
- 性能测试：同一查询冷缓存与热缓存对比，记录 DB 查询数和响应时间。
- 回归测试：现有公开追溯、大屏缓存和库存强一致逻辑不受影响。

## 8. 最终验收标准

1. 新增缓存的查询均可在 Redis 命中时返回，并在未命中时正确从 PostgreSQL 重建。
2. Redis 不可用不导致普通查询整体不可用，除认证闭环和限流等已有强依赖场景外均可降级。
3. 不同合作社、角色和授权仓库之间不存在缓存串数据或越权。
4. 所有相关写事务均在数据库提交后触发缓存失效。
5. 库存最终判断、流水、审计和任务状态仍以 PostgreSQL/任务系统为准。
6. 性能测试证明新增缓存能减少目标查询的数据库压力；没有收益的查询不强行缓存。
7. 具备配置级关闭缓存和自动回源的回滚能力。
8. 缓存 TTL 具有随机抖动，热点 key 支持限并发提前刷新，不出现集中式过期刷新。
